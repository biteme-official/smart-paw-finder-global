# Global Affiliate Program — 정책 결정 스펙 (v2)

> v1(2026-09-18 최초 작성)은 JP·Collabs를 항목별로 단순 비교하는 문서였다. 이번 버전은 실제 구현 순서(DB schema → tracking logic → backend → frontend)에 맞춰, **정책적으로 반드시 결정해야 하는 질문**을 먼저 뽑고, 각 질문에 대해 ①질문 ②Shopify Collabs 참고 기준 ③BITE ME Global 권장안 ④최종 결정값(TBD)을 정리한다.
> **개발자가 임의로 결정해서는 안 되는 값(재무·마진·법무 리스크가 걸린 항목)은 전부 ④에 TBD로 남겨뒀다.** 권장안(③)은 구현을 준비하기 위한 제안일 뿐 확정이 아니다.
> 작성 2026-09-18 · Issue #141 · [기술 설계안](affiliate-program-global.md)

## 0. 목표 UX와 정책이 걸리는 지점

```
로그인 → 상품 페이지 → "Affiliate 버튼" 클릭
   → 해당 상품의 개인 Affiliate Link 생성          ← §7 (가입/활성화가 이 시점에 끝나 있어야 함)
   → 외부 채널에 링크 노출
   → 그 링크로 구매 발생                            ← §1 (Attribution)
   → Affiliate Sales 인정 여부 판정                 ← §2
   → Commission 계산                                ← §3
   → 상태 전이(Pending → Confirmed → Paid)          ← §4
   → 정산 지급                                       ← §5
   (전 구간에서 이상 신호 감지)                       ← §6 (Fraud)
   (전 구간의 근거 조항)                              ← §8 (Legal & Privacy)
```

관리자 승인·이메일 초대 없이 로그인만으로 "상품 페이지에서 바로 링크 생성"까지 가는 구조이므로, §7 활성화 조건과 §1 귀속 로직이 이 문서에서 가장 먼저 확정돼야 하는 두 축이다.

## 1. Attribution

### 1.1 클릭을 무엇으로 기록하는가
- **①** 파트너 링크 클릭을 브라우저 쿠키로만 볼지, 서버 로그로도 남길지, 로그인 여부에 따라 이중화할지.
- **②** Collabs가 쿠키 기반 클릭 추적을 쓰는 것은 확인되나, 쿠키명·서버 기록 여부 같은 기술 구현은 공식 문서에 비공개.
- **③** 이중화 권장 — (a) 브라우저에 attribution 토큰 저장(비로그인 대응), (b) 클릭 이벤트를 서버에 기록(시각·랜딩 URL·**상품 ID**·리퍼러·IP 해시·봇 여부), (c) 로그인 상태면 고객 ID 단위로 서버에 마지막 터치도 기록(기기 이동·인앱 브라우저 대응).
- **④ TBD:** 없음 — 순수 기술 구현이라 이 방식 자체는 개발자가 정해도 되는 영역.

### 1.2 Attribution window
- **①** 클릭 후 며칠 이내 구매까지 그 파트너 실적으로 인정하는가.
- **②** Collabs는 정확한 기본값을 공개하지 않음(머천트가 직접 설정하는 구조로 추정). 업계 관행은 30/60/90일.
- **③** 30일 권장 — JP 원안과 동일하고, §4.2의 Confirmed 전환 타이밍(30일)과도 맞물려 설계가 단순해짐.
- **④ TBD:** **최종 일수는 경영진 확정 필요.** Global은 국가별 구매 결정 주기가 다를 수 있어 30일이 과다/과소일 가능성 있음.

### 1.3 First-click vs Last-click
- **①** 같은 고객이 기간 내 같은 파트너 링크를 여러 번, 또는 서로 다른 파트너의 링크를 각각 클릭했을 때 누구 실적으로 인정하는가.
- **②** 공식 문서에 명시 없음. 업계 표준은 last-click이 압도적 다수.
- **③** Last-click 권장 — 구현이 단순("최근 터치로 덮어쓰기")하고, JP 원안의 "서버측 고객 터치"도 사실상 마지막 터치 저장 구조라 last-click을 이미 전제한다.
- **④ TBD:** **채택 여부는 정책적 확정 필요.** "먼저 소개한 파트너가 실적을 못 가져간다"는 점에 대한 파트너 반발 가능성은 경영진이 감수할 문제.

### 1.4 여러 귀속 접점이 동시에 성립할 때 우선순위
- **①** 캠페인 전용 코드 · 파트너 링크 · 로그인 고객 매칭이 동시에 성립하면 어느 걸 쓰는가. 서로 다른 파트너의 신호가 섞이면?
- **②** 코드-링크 간 우선순위는 Collabs 공식 문서에 비공개.
- **③** JP의 3단 구조 유지 — **코드 > 링크 > 로그인 고객 매칭**. 각 단계 내부에서 파트너가 여럿이면 §1.3의 last-click으로 단일화.
- **④ TBD:** 없음 — 이견 없으면 이 구조로 확정 가능.

### 1.5 클릭한 상품과 실제 구매 상품이 다른 경우 ⚠️
- **①** 파트너가 A 상품 링크를 공유했는데 고객이 그 링크로 들어와 B 상품을 사거나, A와 B를 함께 구매하면 커미션을 어디까지 인정하는가 — **주문 전체(order-level)**로 인정할지, **클릭한 그 상품(line-item-level)**에만 한정할지.
- **②** Collabs는 "Discover"에서 상품 단위로 링크를 발급하는 기능은 확인됐지만, 실제 커미션이 주문 전체에 적용되는지 클릭 상품에 한정되는지는 공식 문서로 확인 불가.
- **③** **Order-level(주문 전체 인정)을 권장.** 클릭 이벤트에는 "어떤 상품 링크로 들어왔는지"를 기록해 파트너 성과 화면에서 상품별 통계는 보여주되, 실제 커미션은 주문 전체 금액 기준으로 계산. 대다수 어필리에이트 프로그램(아마존 어소시에이트 등)이 이 방식이고, line-item 단위 정산은 구현 복잡도가 크게 늘어난다.
- **④ TBD — 개발자가 임의 결정 불가.** Order-level은 "파트너가 저가 상품 하나로 유입시켜 놓고 고객이 고가 상품을 대량 구매하면 커미션 총액이 커지는" 마진 리스크를 안고 간다는 뜻이다. 이 리스크를 감수할지는 경영진이 결정해야 한다.

## 2. Affiliate Sales 기준

### 2.1 어떤 주문을 인정하는가
- **①** 모든 결제완료 주문을 인정하는가, B2B/도매 주문·구독 재결제 등은 제외하는가.
- **②** 명시 규정 없음(스토어프론트 결제 흐름 자체가 전제로 추정 — POS는 클릭 경로 자체가 없어 자연 제외).
- **③** 온라인 스토어프론트에서 파트너 링크/코드로 귀속된 결제완료 주문만 인정. 저장소에 이미 존재하는 **B2B 결제 플로우는 별도 영업채널이므로 기본적으로 제외**를 제안.
- **④ TBD:** **B2B 주문 포함 여부는 세일즈 조직과 조율 필요.** 구독/재구매 상품이 있다면 최초 결제만 인정할지 반복결제도 인정할지도 결정 필요.

### 2.2 매출 집계 기준액
- **①** 커미션 계산 기준액에 상품가·할인·배송비·세금 중 무엇을 포함하는가.
- **②** 정확한 산식은 비공개. "할인 후 상품가, 배송비·세금 제외"가 업계 표준(net sale) 관행.
- **③** JP 원안과 동일 — **할인 적용 후 상품 소계, 배송비·세금 제외**.
- **④ TBD:** 없음 — 업계 표준과 일치해 이견 없으면 채택 가능.

### 2.3 취소
- **①** 확정(Confirmed) 전 주문이 취소되면 커미션은?
- **②** 보류기간 중 취소 → 커미션 자동 취소(확인됨).
- **③** 동일하게 채택 — 즉시 취소, 재계산 없음.
- **④ TBD:** 없음.

### 2.4 부분환불
- **①** 주문 금액의 일부만 환불되면 커미션을 어떻게 조정하는가.
- **②** 공식 문서에 규정 없음("환불·취소에 따라 조정될 수 있다"는 원칙 문구만 존재).
- **③** JP 방식 채택 — **환불 비율만큼 커미션 비례 차감**.
- **④ TBD:** 없음 — Collabs가 공백으로 둔 영역을 JP 규칙으로 메우는 제안.

### 2.5 전액환불
- **①** 확정 전/후로 나눠 처리 방식이 다른가.
- **②** 보류기간 중 전액환불 → 커미션 자동 취소. 확정 이후 환불은 규정 없음.
- **③** 확정 전 = §2.3과 동일 처리. 확정 후는 §4.4에서 별도 규정.
- **④ TBD:** §4.4와 연동해 결정.

## 3. Commission

### 3.1 기본 커미션율
- **①** 신규 가입 파트너에게 기본 적용할 커미션율은?
- **②** 머천트 재량, 공개된 업계 기본값 없음. 상품군별 차등(예: 표준 10%, 저마진 5%)이 일반적 운영 패턴.
- **③** 우선 10%로 제안(JP와 동일, 이해하기 쉬운 기준선).
- **④ TBD — 재무/마진 검토 필요.** 카테고리별 차등(저마진 상품군 인하)을 처음부터 둘지도 결정 필요.

### 3.2 캠페인·상품·파트너별 개별 커미션
- **①** 운영자가 특정 캠페인·특정 상품·특정 파트너에게 기본과 다른 요율을 줄 수 있는가.
- **②** Collabs는 프로그램(캠페인) 단위, 컬렉션(상품군) 단위, invite 프로그램에서는 크리에이터 단위까지 개별 요율 설정을 지원(확인된 사실).
- **③** Collabs와 동일하게 **캠페인 단위 / 상품(컬렉션) 단위 / 특정 파트너 단위** 3축 커스터마이징을 모두 지원하는 캠페인 테이블 설계.
- **④ TBD:** 없음 — 채택 제안.

### 3.3 중복 조건 발생 시 우선순위
- **①** "이 파트너 대상 캠페인"과 "이 상품 대상 캠페인"이 동시에 활성 상태면 어떤 요율을 쓰는가.
- **②** 공식 문서에 중복 규칙 비공개.
- **③** 1차안(JP식): **여러 캠페인이 겹치면 가장 높은 요율**. 대안: **가장 구체적인 조건 우선**(파트너+상품 특정 > 파트너만 특정 > 상품만 특정 > 전체 캠페인).
- **④ TBD — "최고 요율" vs "최다구체조건 우선" 중 선택은 마케팅팀이 결정.** 의도치 않은 요율 스태킹(여러 캠페인이 겹쳐 예상보다 높은 커미션이 나가는 상황)을 막기 위해 실제 캠페인 운영 시나리오를 놓고 정해야 함.

## 4. Commission Status

### 4.1 Pending
- **①** 언제 Pending 상태가 생성되는가.
- **②** 결제(주문) 발생 즉시 Pending 마킹, 보류기간 동안 유지.
- **③** 동일 — 주문 confirmed 웹훅 수신 시점에 Pending 레코드 생성.
- **④ TBD:** 없음.

### 4.2 Pending → Confirmed
- **①** 무엇을 근거로 전환하는가 — 단순 기간경과인가, 배송완료 같은 추가조건이 있는가.
- **②** 보류기간(1~90일, 기본 30일) 경과 + 그 기간 내 취소/전액환불 없음 → 자동 Confirmed.
- **③** 동일 — 주문일+30일(§1.2와 연동) 경과 + 취소/전액환불 이력 없음 → 자동 Confirmed. **배송완료는 조건에 넣지 않음**(국가별 배송기간 편차가 커서 배송 연동 시 정산이 지나치게 늦어짐).
- **④ TBD:** 30일 자체는 §1.2에서 결정.

### 4.3 Confirmed → Paid
- **①** Confirmed 이후 언제 실제 지급으로 넘어가는가.
- **②** 월 2회 자동 정산 배치에서 그 시점까지 Confirmed인 금액을 지급.
- **③** 정산 배치(§5.2 주기와 연동)에서 Confirmed 상태 금액을 지급 처리.
- **④ TBD:** 정산 주기는 §5에서 결정.

### 4.4 환불/취소 발생 시 상태별 처리
- **①** Pending 중, Confirmed 후(정산 전), Paid 후(이미 지급 완료) 각각 환불/취소가 들어오면 어떻게 처리하는가.
- **②** Pending 중 취소/전액환불 = 자동 커미션 취소(확인됨). Confirmed·Paid 이후 환불 처리는 공식 문서에 규정 없음.
- **③** Pending 중 = 즉시 취소(Collabs와 동일). Confirmed 후(정산 전) = 상태를 `void`로 바꾸고 다음 정산 배치에서 제외. Paid 후 = **클로백 대상**으로 별도 원장에 기록.
- **④ TBD — Paid 이후 클로백을 실제로 집행할지(다음 정산에서 차감 vs 손실 처리)는 재무 정책 결정 필요.** JP 원안도 이 케이스를 명확히 규정하지 않은, Global이 새로 정해야 하는 영역.

## 5. Payout

### 5.1 최소 지급액
- **①** 얼마 이상 쌓여야 지급하는가.
- **②** $25 USD (크리에이터 쪽 자동정산 기준, Hyperwallet 경유).
- **③** 스토어 통화 기준으로 Collabs의 $25 상당액을 참고해 국가별 환산 문턱 설정.
- **④ TBD — 정확한 금액과 통화 기준은 재무팀 확정 필요.**

### 5.2 지급 주기
- **①** 월 1회인가, Collabs처럼 월 2회인가.
- **②** 월 2회.
- **③** 우선 월 1회로 시작(JP 원안, 정산 검증 부담을 줄이기 위해) — 안정화 후 월 2회로 늘리는 방향 제안.
- **④ TBD:** 최종 주기는 운영팀 결정.

### 5.3 정산 통화
- **①** 주문이 발생한 스토어 통화 그대로 지급하는가, 단일 기준통화로 환산하는가.
- **②** 지급은 USD 기준, 비-USD 선택 시 환전수수료 발생.
- **③** Global도 **단일 기준통화(예: USD) 지급**을 권장 — 다국가 파트너에게 여러 통화로 개별 지급하는 인프라를 초기부터 구축하는 것은 과함.
- **④ TBD:** 기준통화를 USD로 할지, 본사 소재국 통화로 할지는 재무 결정 필요.

### 5.4 지급 수단
- **①** 은행 송금 / PayPal / Wise 등 무엇을 쓰는가.
- **②** Collabs 자체 Hyperwallet 인프라(Shopify가 구축한 전용 결제 레일) — Global엔 이에 상응하는 인프라가 없음.
- **③** 기존 국제송금 서비스(PayPal / Wise 등) 연동을 권장 — 직접 은행망을 구축하는 것보다 훨씬 빠르게 시작 가능.
- **④ TBD — 결제·재무 인프라 계약이 필요한 영역이라 개발자가 임의 결정 불가.** 어떤 서비스를 쓸지는 경영진·재무팀이 결정.

### 5.5 환율 처리
- **①** 스토어 통화 매출을 기준통화로 환산할 때 어느 시점 환율을 쓰는가.
- **②** 비공개.
- **③** **주문 확정(Confirmed) 시점의 환율** 적용을 제안 — 정산 시점 환율보다 예측 가능성이 높음.
- **④ TBD:** 환율 데이터 소스(Shopify 자체 환율 vs 외부 API)는 재무 결정 필요.

### 5.6 수수료 부담 주체
- **①** 해외송금·환전 수수료는 회사 부담인가 파트너 부담인가.
- **②** 크리에이터가 비-USD 수취 시 환전수수료 부담(확인됨).
- **③** Collabs와 동일 — 환전수수료는 파트너 부담, 기본 송금수수료는 회사 부담을 제안.
- **④ TBD:** 최종 부담 주체는 재무 결정 필요.

### 5.7 지급 실패 처리
- **①** 계좌정보 오류 등으로 지급이 실패하면?
- **②** 명시 규정 없음(세금정보 미제출 시 지급 상한을 적용하는 유사 패턴만 존재).
- **③** 지급 실패 시 해당 금액을 "지급대기"로 원장에 유지, 파트너에게 재확인 알림. 일정 기간(JP 원안 참고 6개월) 미해결 시 이월 처리.
- **④ TBD:** 유예 기간과 최종 미해결 시 처리(몰수 vs 무기한 보관)는 정책 결정 필요.

## 6. Self-referral & Fraud

### 6.1 본인 구매 판정
- **①** 무엇을 근거로 "본인 구매"로 판정하는가.
- **②** 명시 규정 없음.
- **③** JP 방식 — **주문 고객의 Shopify Customer ID 또는 이메일이 파트너 계정과 일치하면 자동 마킹, 커미션 0.** 결제 자체는 막지 않음.
- **④ TBD:** 없음 — 채택 제안.

### 6.2 중복계정 판정
- **①** 한 사람이 여러 파트너 계정을 만드는 것을 어떻게 막는가.
- **②** 명시 규정 없음(크리에이터가 한 시점에 프로그램 하나에만 속한다는 제약은 참고 수준으로 확인).
- **③** **Shopify Customer Account(로그인 계정) 1인 1파트너 계정**을 시스템적으로 강제 — 동일 Customer ID 재가입 시도 시 기존 계정으로 안내.
- **④ TBD:** 이메일을 바꿔 새 Shopify 계정을 만드는 우회는 시스템적으로 막기 어려움 — 탐지 로직 고도화는 별도 과제로 남김.

### 6.3 비정상 주문/클릭 판정 (정량 임계값)
- **①** 짧은 시간 내 다량 클릭, 동일 IP 반복 주문 등을 어떤 수치 기준으로 이상 탐지하는가.
- **②** 공개된 수치 기준 없음. "SNS 이상활동", "무단 유료광고 집행"을 이의제기 트리거로 언급하나 구체 임계값은 비공개.
- **③** 관리자 화면에 "자기구매 의심" · "한 파트너의 급증" · "신규 파트너 첫 주문"을 우선 플래그로 노출(JP 원안)하고, 초기에는 자동 차단 대신 **사람이 검토**하는 방식으로 시작.
- **④ TBD — 구체적 수치 임계값(시간당 클릭 n회, 동일 IP 주문 n건 등)은 개발자가 임의로 정하지 않는다.** 운영 데이터가 쌓인 뒤 정책팀이 데이터 기반으로 정해야 하는 영역. 초기값은 "1단계는 수동 검토"로 명시.

### 6.4 쿠폰/링크 오남용
- **①** 캠페인 코드가 쿠폰 사이트에 유출되거나, 파트너가 유료광고로 링크를 무단 홍보하면 어떻게 대응하는가.
- **②** 둘 다 자동 이의제기(auto-dispute) 트리거로 공식 확인됨.
- **③** 코드는 **고객당 1회 + 총 사용 횟수 상한 + 기간 종료**로 유출 손해를 제한(JP 원안). 무단 유료광고는 약관상 금지 조항 + 발견 시 수동 검토로 시작.
- **④ TBD:** 자동 탐지 도구 도입 여부는 §6.3과 함께 추후 결정.

### 6.5 위반 시 제재 기준
- **①** 어떤 경우에 "해당 건만 불지급"이고 어떤 경우에 "계정 정지 + 보류 커미션 전액 취소"인가.
- **②** 단계적 제재(커미션 0% → 보류지급 취소 → 연결 해제 → 영구 차단)가 확인됨. 등급을 가르는 구체 기준 자체는 비공개.
- **③** 1회성·경미(단순 자기구매 1건 등) = 해당 건만 커미션 0. 반복·중대(다계정 우회, 코드 대량유출, 명백한 허위정보) = 계정 정지 + 보류 커미션 전액 취소.
- **④ TBD — "경미"와 "중대"를 가르는 구체 기준선은 법무/정책팀이 최종 확정.** §6.3과 마찬가지로 초기엔 사람이 판단하고 이후 규칙화.

## 7. Eligibility

### 7.1 가입 가능 국가
- **①** 특정 국가 거주자만 가입 가능하게 제한하는가.
- **②** Open-access 프로그램은 현재 미국·영국·캐나다로 제한(공식 확인).
- **③** Global몰은 다국가 대상이므로 **원칙적으로 국가 제한 없음**을 제안. 단, §5.4(지급수단)가 못 커버하는 국가는 가입·활동은 가능하되 지급 시점에 별도 안내.
- **④ TBD:** 실제 지급 가능 국가 목록은 §5.4 확정 후 함께 결정.

### 7.2 연령 기준
- **①** 최소 연령은.
- **②** 명시 규정 확인 안 됨.
- **③** JP 원안과 동일하게 **만 18세 이상 확약 체크박스** 유지.
- **④ TBD:** 없음 — 채택 제안.

### 7.3 활성화 조건
- **①** 로그인 외에 추가로 요구할 조건이 있는가(팔로워 수 등).
- **②** Open-access는 정량조건 없이 즉시 활성화.
- **③** **정량조건 없음** — 로그인 + 신청폼 제출 + 18세 확약 + 약관동의로 즉시 활성화(이번 스펙에서 이미 확정한 방향).
- **④ TBD:** 없음 — 확정.

### 7.4 탈퇴 및 재가입
- **①** 파트너가 스스로 탈퇴할 수 있는가. 탈퇴/정지 후 재가입은 언제부터 가능한가.
- **②** 자진 탈퇴 관련 공식 규정 비공개. 위반으로 인한 차단은 "최종적이며 번복 불가"로 명시.
- **③** JP 원안대로 셀프 탈퇴 버튼 제공, 탈퇴 즉시 링크·코드 무효화. **자진 탈퇴 후 재가입은 즉시 허용**(자발적 탈퇴는 위반이 아니므로). 위반으로 인한 정지는 Collabs처럼 재가입 불가를 기본값으로 제안.
- **④ TBD:** 정지 후 "영구 재가입 불가"가 과한지, 일정 기간(예: 1년) 후 재심사 여지를 둘지는 정책팀 결정.

## 8. Legal & Privacy

### 8.1 Affiliate Program Terms 신설 — 필요 조항
- **①** 지금 없는 Global용 Affiliate Program Terms를 새로 만들어야 하는데, 최소한 어떤 조항이 필요한가.
- **②** 크리에이터는 Shopify의 Community Guidelines + 개별 브랜드와의 파트너십 계약이라는 이중 구조를 따름. 확인된 필수 조항 유형: 금지행위, 세금 책임, 위반 시 제재·불지급, 결제수단 활성화 요건.
- **③** 최소 아래 조항 포함 제안 —
  1. 참여자격·활성화 조건(§7)
  2. 링크/코드 사용범위 및 금지행위(§6)
  3. 귀속·정산 규칙 요약(§1~5 인용)
  4. 위반 시 제재(§6.5)
  5. 세금 책임은 파트너 본인에게 있다는 조항
  6. 프로그램 변경/종료 시 통지 방법
  7. 준거법·분쟁해결
- **④ TBD — 조항의 구체 법률 문구(준거법 국가, 분쟁해결 관할, 면책 범위 등)는 이 문서에서 확정하지 않는다. 법무 검토·승인 필수.**

### 8.2 기존 Privacy Policy 수정 필요 항목
- **①** Affiliate 기능을 추가하면서 기존 개인정보처리방침에 새로 넣거나 수정해야 할 항목은.
- **②** Collabs 전용 개인정보 조항은 별도 공개돼 있지 않음(Shopify 전체 정책에 포함되는 것으로 추정).
- **③** 아래 항목 추가를 제안 —
  1. 클릭 로그(IP 해시·랜딩페이지·리퍼러) 수집 목적·보관기간
  2. 파트너 식별을 위한 Shopify Customer ID/이메일 활용 근거
  3. 파트너 정산을 위해 수집하는 결제정보(계좌 등)를 제3자(§5.4 지급수단, 예: PayPal/Wise)에 위탁하는지 여부
  4. 해외 지급수단 사용 시 발생하는 국가 간 데이터 이전
- **④ TBD — GDPR/CCPA 등 대상 국가별 적용 규제 여부, 실제 보관기간 수치, 제3자 위탁 조항 문구는 법무 검토 필요. 이 문서에서 확정하지 않는다.**
