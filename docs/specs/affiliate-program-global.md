## 1. 현재 글로벌몰 구조와의 충돌 — 결정 필요

**기존(PR #110, 현재 라이브):** 셀프 가입 → 신청 즉시 전원에게 `PETNAME15` 형태의 **15% 할인 코드 1개**를 발급 → Google Sheets에 신청 내역 기록. 커미션 추적·정산·링크 귀속 자체가 없다. 승인 절차는 없지만 "고객 할인 코드"가 기본값이라는 점이 JP 설계안과 반대다.

**JP 설계안의 핵심 결정:** 기본 층은 **코드 없이 링크만** 지급하고, 고객 할인은 운영자가 고른 캠페인에만 얹는다. 이래야 "코드가 쿠폰 모음 사이트로 새는" 문제와 "할인 자판기" 문제가 애초에 안 생긴다.

이 둘은 같은 문제를 정반대로 풀고 있다. 글로벌 버전을 만들려면 아래 중 하나를 확정해야 한다.

- **A. JP 방식으로 전환** — 신규 가입자부터 코드 미발급, 링크만 지급. 커미션 정산 체계를 새로 구축(§3~§6). 기존 15% 코드는 캠페인 성격의 특전으로 재정의하거나 단계적으로 종료.
- **B. 현행 방식 유지 + 커미션만 추가** — 전원 15% 코드는 그대로 두고, 그 위에 링크 기반 커미션 추적만 얹는다. "코드 유출" 리스크는 원본 설계보다 커지지만 마이그레이션 충격은 작다.
- **C. 하이브리드** — 신규 가입자는 A안(링크만), 기존 가입자는 코드 유지 후 자연 소멸.

아래 §2 이후는 **A안(JP 원안 방식)을 기본값으로 가정**하고 작성했다. B/C를 택하면 §3(두 층 구조)과 §7-03(코드 유출 통제)이 바뀐다.

## 2. 참여 구조 — 셀프 가입

문은 활짝 열고, 우대만 골라서 얹는다는 원안의 원칙은 그대로 가져온다.

| 항목 | 현재(Collabs 부재, PR #110) | 글로벌 버전 제안 |
|---|---|---|
| 참여 | 셀프 가입, 승인 없음 | 셀프 가입, 승인 없음 (유지) |
| 로그인 | 이메일 입력만 (계정 불필요) | **Shopify Customer Account 로그인 필수** — 귀속·중복가입 방지의 전제조건 |
| 발급물 | 전원 15% 할인 코드 | 전원 전용 링크 `biteme.one/a/CODE`, 할인 코드는 캠페인 대상자에게만 |
| 데이터 | Google Sheets | KV 원장 (§6) |

### 가입 흐름
1. `/affiliate` 페이지에서 "Sign up with your account" 버튼 (Shopify Customer Account 로그인 유도)
2. 로그인 후 이름·SNS 핸들·18세 이상 확약·이용약관 동의 — 동의 버전·시각 기록
3. 즉시 전용 링크 `biteme.one/a/{code}` 발급
4. 링크 복사 버튼 + "내 성과" 화면으로 이동

기존 PR #110의 신청 폼(소셜 계정+국가+유입경로)은 그대로 재사용 가능 — 로그인 게이트만 앞에 추가하면 된다.

## 3. 두 층 — 기본과 캠페인

| 층 | 대상 | 고객 할인 | 커미션 | 발급물 |
|---|---|---|---|---|
| 기본 | 가입한 전원 | 없음 | (결정 필요 — JP는 10%) | 링크만 |
| 캠페인·지정 파트너 | 운영자가 고른 파트너 | 0~15% | 기본보다 높게 | 링크 + 전용 코드(할인 있을 때만) |
| 캠페인·전원/상품 | 기간·상품 한정, 전원 대상 | 없음 | +α | 없음 |

요율 해석 순서, 주문 시점 요율 고정, 커미션 기준액(할인 후 상품 소계, 배송비·세 제외) 등 계산 규칙은 원안과 동일하게 가져간다 — 통화만 스토어 결제 통화를 따른다(고정 ¥ 표기 없음).

캠페인이 도는 방식(관리자 화면에서 캠페인 생성 → 대상 지정 → 저장 시 코드 자동 발급 → 대상자 알림)도 원안과 동일. 다만 **LINE 푸시 대신 이메일 알림**(또는 마이페이지 인앱 알림)으로 대체.

## 4. 귀속 설계

원안의 3단계 귀속(코드 > 링크 > 고객)을 그대로 가져오되, 3번째 갈래의 정체성 신원 확인 수단만 바뀐다.

1. **코드 귀속** — 캠페인 전용 코드가 주문에 붙어 있으면 우선 (창 제한 없음)
2. **링크 귀속** — 파트너 링크 클릭이 30일 안에 있었으면 (창 기간은 Global 반품정책 확인 후 재검토 — JP는 7일 반품정책 기준 30일로 산출)
3. **고객 귀속** — 이 고객이 **Shopify Customer Account로 로그인한 상태**에서 30일 안에 누군가의 링크를 눌렀으면. 브라우저가 아닌 서버에 고객 ID 단위로 터치를 남기므로 기기를 바꾸거나 인스타/이메일 인앱 브라우저를 벗어나도 귀속이 따라온다.

링크가 주문까지 살아남는 경로(파트너 링크 → 클릭 기록(30일 저장) → 카트 속성에 파트너 참조 한 줄 → 주문 수신 시 판정 → 확정 대기 → 주문일+30일 후 확정)도 원안과 동일한 구조로 이식 가능. **카트 속성에 한 줄 추가하는 지점이 가장 위험한 변경**이라는 원안의 경고는 그대로 유효 — 결제 경로 변경은 반드시 단독 배포.

## 6. 기록하는 것 (Vercel KV 원장)

Supabase 테이블 대신 KV 키 네임스페이스로 설계. 기존 `api/affiliate.ts`가 이미 쓰는 `affiliate:app:{id}`, `affiliate:email:{email}`, `affiliate:ids` 패턴을 확장한다.

| 원장 | KV 키 패턴(안) | 역할 |
|---|---|---|
| 파트너 | `affiliate:partner:{id}` | 코드·고객ID·SNS·약관 동의 버전/시각·18세 확약 |
| 캠페인 | `affiliate:campaign:{id}` | 이름·기간·커미션율·할인율·대상 |
| 캠페인 전용 코드 | `affiliate:campaign-code:{code}` | 캠페인 참조, 저장 시 생성·종료 시 비활성 |
| 클릭 | `affiliate:click:{id}` | 시각·랜딩·리퍼러·IP 해시·봇 여부 |
| 고객 터치 | `affiliate:touch:{customerId}` | 로그인 고객의 서버측 마지막 터치 |
| 전환 | `affiliate:order:{orderId}` | 귀속 방식·기준액·요율·커미션·상태·확정 예정일 (주문 1건=1행, 중복 방지) |
| 정산 | `affiliate:settlement:{period}:{partnerId}` | 총액·순액·상태·지급일·이의신청 마감일 |

개인 식별 정보 최소화 원칙(IP 해시만, 계좌정보는 초기 단계에 담지 않음)은 원안 그대로 유지.

## 7. 새는 곳과 통제

| # | 문제 | 대응 |
|---|---|---|
| 1 | 자기 링크로 자기 구매 | 주문 고객의 Shopify Customer ID·이메일이 파트너와 같으면 자기구매로 적재, 커미션 0. 결제는 막지 않음 |
| 2 | 계정 하나에 파트너 하나 | Shopify Customer Account 1인 1계정이 다계정 우회를 막는 가장 싼 방법 (LINE 대신 Shopify 로그인이 이 역할 수행) |
| 3 | 전용 코드 유출 | 고객당 1회 + 총 사용 횟수 상한 + 기간 종료. §1에서 B/C안을 택하면 이 리스크가 원안보다 커짐(전원 코드 보유) — 별도 통제 강화 필요 |
| 4 | 링크 귀속 유실 | 서버측 고객 터치로 보강(§4 3번째 갈래) |
| 5 | 주문 데이터 중복·유실 | 주문 1건=1행, 일 1회 재대사 |
| 6 | 환불·취소 | 환불 알림 즉시 차감, 확정 직전 재확인 |
| 7 | 코드 충돌 | 현재 Global에 웰컴/증정 코드가 있는지 확인 필요 — 있다면 Shopify 주문당 코드 1개 제한과 충돌 가능 |
| 8 | 계좌 정보 | DB 평문 저장 금지, 초기 단계는 명세만 |
| 9 (신규) | **법무·세무 공백** | 계약 법인, 대상 국가별 소득세/원천징수, 이용약관 준거법 — 전부 미정. 구현 전 법무 확인 필수 |

## 8. 단계 계획 (날짜 미정 — Phase 구조만)

| Phase | 내용 | 비고 |
|---|---|---|
| 0. 장부 세우기 | 파트너 원장, 주문 수신 시 코드 매칭, 관리자 목록(읽기 전용) | 기존 PR #110의 KV 스키마 확장 |
| 1. 링크 귀속·확정·회수 | 파트너 링크 라우트, 클릭 기록, 카트 속성, 서버측 고객 터치, 확정/환불 처리 | 결제 경로 변경은 단독 배포 (CLAUDE.md 프론트 안전 규칙: `api/`, `vercel.json` Maintainer 확인 필수) |
| 2. 문 열기 | 로그인 게이트 추가, §1 결정에 따른 코드 발급 방식 변경, 파트너 성과 화면 | 이미 라이브인 기존 가입 폼과의 마이그레이션 포함 |
| 3. 캠페인·정산 | 캠페인 등록, 전용 코드 발급, 월 마감·명세, 이상 감지 | 세무/법무 확인 완료 후 |

배포 3원칙(읽기→쓰기→노출 / 결제 경로 단독 배포 / 기존 주문 처리 절대 안 죽임)은 원안 그대로 가져온다.

## 9. 결정이 필요한 항목

| 항목 | 확인 필요 사항 |
|---|---|
| §1 구조 | A(JP 링크식) / B(현행 코드 유지) / C(하이브리드) 중 선택 |
| 기본 커미션율 | JP는 10% — Global도 동일하게 갈지 별도 확정 |
| 귀속 창·확정 대기 기간 | Global 실제 반품정책 확인 후 30일 유지 여부 결정 |
| 계약 법인·준거법·세무 | 어느 국가 법인/세율 기준으로 약관을 쓸지 |
| 코드 충돌 | 기존 웰컴/증정 코드 존재 여부 확인 |
| 통화 표기 | 커미션·정산 금액을 스토어 통화(currencyCode) 그대로 쓸지, 기준 통화(USD 등)로 환산해 관리자 화면에 통일 표시할지 |
